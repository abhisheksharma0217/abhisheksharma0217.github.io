The problem

Every instrument adds a maintenance path.

A psychological test can have its own data structure, report layout, age range, and export requirements. Supporting a new instrument requires coordinated changes across database records, application code, templates, and reporting configuration.

My work on e-Testing connected these pieces into a maintainable workflow for a hospital intranet application. The responsibility extended through ongoing changes, deployment, and the documentation needed for a successor to continue the work.

The system

From stored results to accessible reports.

The Flask application connects a MariaDB database with search, instrument-specific result pages, report links, and automated CSV processing. It runs on a Linux server through Apache and mod_wsgi, with LDAP-backed sign-in.

My contribution

Maintain the application and the change process.

  • Application development: maintained result lookup, instrument-specific routes, report templates, and the data connections supporting them.
  • Reporting automation: generalized the CSV-processing workflow around per-instrument configuration and YAML mappings.
  • Instrument integration: documented the coordinated changes needed across the database, application, report links, and exports.
  • Operational handover: prepared practical documentation for source control, development-to-production changes, and file and directory permissions.

Engineering decisions

Make recurring changes explicit.

Move instrument variation into configuration

The generalized CSV pipeline uses instrument-specific configuration and YAML mappings. This gives maintainers a defined place to describe export behaviour and removes reliance on hard-coded instrument prefixes in the shared workflow.

Follow the entire lookup path

A valid report route is one dependency in a longer chain. During an instrument addition, a missing entry in the application's main instrument lookup prevented the report from being found. Tracing that dependency shaped the handover instructions for future additions.

Treat permissions as part of deployment

Moving a working change onto the production server can introduce ownership and access differences. The handover covers permissions for both individual files and complete directories, alongside the source-control workflow.

Technical handover

Leave a system someone else can maintain.

The handover is organised around the tasks a successor needs to perform: obtain the project, work with the main branch, move changes into production, and add or update an instrument.
